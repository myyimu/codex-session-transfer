# Codex 任务连续性：产品策略、界面与开发计划

更新时间：2026-08-20

[English version](./product-strategy.en.md)

## 结论

恢复能力有价值，但不应把产品定位成低频的“全量灾难恢复工具”。更准确、也更可持续的定位是：**一个本地优先的 Codex 任务连续性工具，帮助用户迁移、备份、检查，并让仍在本机的数据重新可用。**

核心用户不是偶尔丢一次数据的人，而是有多个项目、跨设备开发、会长期保留重要任务上下文的 Codex 重度用户。对他们而言，一条任务失去可见性不只是少了一段聊天记录，而是丢失了需求背景、决策过程、工具执行轨迹和继续协作的入口。

## 研究摘要

公开信号支持“本地任务可见性与可移植性”这个问题真实存在，但样本仍偏早期用户社区，不能据此推断为大众高频需求。

- OpenAI 说明 Codex 在桌面端是独立视图，历史与 ChatGPT 历史分离，并且本地任务留在电脑上。这使本地导出、备份和迁移成为独立且合理的需求，而不能期待普通 ChatGPT 同步自动覆盖它。[OpenAI Help Center](https://help.openai.com/en/articles/20001275-chatgpt-work-and-codex)
- Codex 的公开 issue 有用户报告：聊天仍在本地，但桌面端无法正确发现、索引、关联或显示它们；用户明确提出需要安全的重新索引或恢复机制。[Issue #23999](https://github.com/openai/codex/issues/23999)
- 另一个桌面端问题中，GUI 看起来丢失了数月历史，但 CLI 中仍能看到正确内容。这说明“会话内容还在，呈现层失配”是一个比物理文件损坏更直接的产品机会。[Issue #17354](https://github.com/openai/codex/issues/17354)
- 社区里已有独立工具聚焦离线打包、预览、路径映射和跨设备导入，也明确避开云同步和账号状态迁移。这验证了场景存在，同时说明产品需要用安全、可解释的本地工作流区分自己。[社区案例](https://www.reddit.com/r/OpenaiCodex/comments/1u569yb/unofficial_localfirst_codex_session_exportimport/)

这些证据带来的推断是：市场规模可能是利基型，但单次问题的上下文损失和切换成本很高。产品不需要靠每天使用来证明价值；它应像可靠的迁移工具和保险装置一样，在换机、项目归档和侧边栏异常时成为默认选择。

## 功能价值与取舍

| 能力 | 用户价值 | 当前状态 | 产品决策 |
| --- | --- | --- | --- |
| 选择性导出、导入、逐项目路径映射 | 高：覆盖换机、备份和项目交接 | 已实现 | 继续作为主流程；导入前显式确认每个项目的本机目录 |
| 任务数据库、索引、项目状态重新登记 | 高：解决“文件在，侧边栏不见” | 已实现 | 保持为可解释、可选择的修复动作 |
| 标题和首条用户消息兼容清理 | 中：恢复可搜索性与可读性 | 已实现内部兼容处理 | 不作为反复出现的健康或修复信号 |
| 写入前退出保护和本地快照 | 高：避免二次损失 | 已有 | 保持为不可绕过的安全门 |
| 导入前清单、路径映射与冲突预览 | 高：让用户理解影响再写入 | 已实现核心流程 | 继续优化逐任务解释和拒绝原因 |
| 现有任务的安全 JSONL 合并 | 高但有风险：保留备份后续聊 | 已实现受限预览与追加式合并 | 仅显式选择且通过安全判断时执行；否则跳过 |
| 归档状态、内部子任务关系、缓存与排序修复 | 中：改善侧边栏秩序 | 部分或未实现 | 仅在可验证字段上渐进支持 |
| 长期记忆数据库合并与重新汇总 | 低频、高复杂度、高兼容风险 | 未实现 | 不进入核心承诺；只保留研究与导出证据能力 |
| 整个数据目录覆盖 | 风险远高于收益 | 不做 | 明确禁止 |

## 定位与信息架构

产品定位统一使用“Codex 任务连续性”，副标题使用“迁移、备份、检查和重新找回本地任务”。当前安装包和窗口名称仍使用“Codex 会话迁移”，仓库名保留 `codex-session-transfer`；后续改名时应一次性同步安装包、窗口、README 和应用内品牌文案。

顶层始终只有两个视图：

1. **任务库**：发现、筛选、导出、检查本机任务，并在确认后修复可见性。
2. **导入归档**：检查 ZIP、比较本机状态、逐项目确认本机路径并执行可回退导入。

“健康检查”“修复建议”“冲突详情”“操作回执”均为当前视图中的可折叠面板或右侧抽屉，避免形成第三个需要理解的新模块。

## 界面排版与交互

### 任务库（导出）

顶部保持轻量标题栏，显示任务数量和扫描状态；当前 Codex provider、模型及运行状态收在应用侧栏底部。只有存在“任务未显示”这类可执行问题时才出现低对比恢复提示，不向普通用户展示坏标题、数据库一致性或其他技术计数。

主体采用紧凑的桌面级任务库布局：

- 独立工具栏放任务搜索、项目筛选、排序说明和“全选已显示任务”。
- 主栏增量渲染任务列表，展示标题、项目、最后活动时间、会话轮数和状态标签；大量历史通过滚动继续加载。
- 底部固定操作栏展示已选数量和体积，包含“导出压缩包”和仅对可修复任务开放的次级修复动作。

交互规则：扫描到的任务立即显示，扫描可取消，超时后可从内存续扫。恢复提示打开右侧操作抽屉，任务按项目分组、可搜索且默认不选中；普通界面只说明可重新显示的任务数和写入前会创建安全备份。完成后显示简短结果，并允许进入本地快照管理；技术原因和非行动项默认隐藏。

### 导入归档（导入）

导入页采用从上到下的单一决策流，避免用户在文件、项目和冲突设置之间来回跳转：

1. 顶部为 ZIP 投放区；解析后显示所选文件、任务数和打包时间。
2. 任务列表逐行显示新任务、重复任务及其默认动作；重复任务可选择跳过或从本地历史恢复。
3. 只有通过安全追加预览的重复任务才显示逐任务“合并续聊”开关，并给出可追加记录数或拒绝原因。
4. 路径映射面板按归档项目列出原路径、本机候选和确认状态；唯一候选自动预选，多候选或无候选时要求用户选择现有目录。
5. 底部固定确认区显示新增、恢复、合并或待确认映射的最终数量，主按钮使用明确的“确认映射并导入”。

重复任务默认只跳过，不覆盖。用户可以切换为“从本地历史恢复”，并对通过安全判断的单个任务额外选择“合并续聊”。合并前必须展示是否可安全追加、可追加记录数和拒绝原因；不能在没有预览的情况下覆盖 JSONL。历史项目目录缺失时必须由用户选择现有本机目录，或让没有记录项目路径的任务保持未绑定，绝不创建占位目录。

### 视觉原则

延续当前的轻盈本地工具感：白色留白、低对比水彩纹理、导出使用青色、导入使用玫瑰色。风险不使用大面积警告红，而用琥珀色提示“需要决定”；真正不可执行的条件才使用红色。每一步优先展示用户结果，例如“3 条任务可重新出现”，而不是“写入 state_5.sqlite”。

## 当前交付状态与后续计划

### 已完成：可判断、可确认

- 两个顶层视图内已经提供渐进任务扫描、可见性恢复提示、归档预览和重复任务状态。
- 正常界面只展示可操作的“任务未显示”建议；数据库一致性等技术诊断保留在内部。
- 导入和修复写入前会创建本地快照，完成后生成操作回执。
- 默认语义保持保守：新增任务导入，已有任务跳过；重新登记和安全合并都需要用户显式选择。

验收：用户无需理解内部数据库，也能在写入前说清“哪些任务会改变、为什么、如何回退”。

### 已完成：受限的安全续聊合并

- 已有任务可以先预览 JSONL 是否能安全追加，仅在顺序和公共历史满足约束时开放“合并续聊”。
- 无法可靠判断、记录截断或历史不兼容时不执行猜测性覆盖，用户仍可选择仅重新登记或跳过。
- 导入时保留可验证的来源和任务元数据，不擅自构造未知的父子关系。

验收：备份后继续产生的消息不会因为恢复而丢失，任何无法可靠判断的冲突都会停在预览态。

### 进行中：可维护与兼容演进

- 导入与修复已经保留轮换的操作回执和可按需管理的本地快照；快照不会自动删除。
- 任务库验证、数据库可读性和登记一致性检查保留为内部诊断，不在正常界面暴露技术计数。
- 持续跟随 Codex 本地数据模型变化，只有在证据充分时才扩展归档状态、来源和侧边栏可见性修复。
- 后续重点是补充真实桌面环境回归、更新 README 截图，并继续验证跨版本兼容性。

验收：用户可以从一次操作的回执追溯原因、影响和回退点，不依赖记忆或终端日志。

### 暂不排期

- 长期记忆数据库、`MEMORY.md` 或汇总水位的导入与重算。
- 全目录覆盖、自动清理缓存或强制改写侧边栏排序。
- 未被稳定数据模型明确支持的内部协作父子图恢复。

这些能力涉及未公开且演进中的内部状态，错误恢复的代价高于缺少它们的收益。若未来要做，应先以“只读盘点和证据导出”开始，而不是直接写入。

## 成功指标

- 用户在导入前能理解每个任务的默认动作与风险。
- 关键任务在换机或侧边栏异常后能重新打开并继续使用。
- 每次写入都有本地快照和人类可读回执。
- 产品不上传任务内容，也不以云同步、账号迁移或长期记忆恢复作为卖点。
